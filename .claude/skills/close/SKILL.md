# close (GitHub)

Обёртка над плагинным `ledger:close`. Поведение оригинала сохраняется целиком;
заменяются только шаги, которые ходят в трекер — вместо Linear используется
`gh` и GitHub Issues.

## Как читать оригинал

Найди оригинальный SKILL.md динамически, версию не хардкодь:

```bash
ls -d ~/.claude/plugins/cache/ledgerloop/ledger/*/skills/close/SKILL.md | sort -V | tail -1
```

Если команда ничего не вернула — скажи пользователю, что плагин `ledger` не
установлен, и остановись. Иначе прочитай найденный файл и следуй ему дословно:
запуск `/ledger:log`, формулировка lossy-правила, перенос спеки в `tasks/done/`,
правила staging и коммита (никаких `--no-verify`, при провале хука — новый
коммит, не amend), запрет пуша в дефолтную ветку, форма отчёта. Логи слоёв
пишет агент `ledger:scribe` — здесь ничего не меняется. Ниже — только замены.

Если лог слоя вышел за бюджет `budgets.logEntries` — сначала `/ledger:fold`,
как в оригинале.

## Проверка окружения

Перед первым сетевым вызовом выполни `gh auth status`. Если gh не
авторизован — скажи об этом прямо (`gh auth login`) и остановись, ничего не
закрывая и не пуша.

Репозиторий вычисляй при каждом запуске из `ledgerloop.config.json`:
`<tracker.team>/<tracker.project>` (сейчас `ArghTeam/razdacha`). Не хардкодь.
Все вызовы `gh` — с явным `-R <repo>`.

## Замена шага 1 — определение номера issue

Аргумент принимается в любой из форм: `12`, `#12`, URL issue. Приведи к голому
числу `<N>`.

Если аргумента нет:

1. Возьми текущую ветку (`git rev-parse --abbrev-ref HEAD`) — она имеет вид
   `<handle>/<N>-<slug>`, номер это сегмент `<N>`.
2. Если из ветки номер не выводится — поищи спеку в `tasks/` и возьми поле
   `tracker` из её фронтматтера (там номер вида `"#12"`).
3. Если и так не вышло — спроси пользователя, не угадывай.

Спеку ищи как `tasks/<N>-*.md`. Если её нет — это тривиальная правка мимо
`/capture` и `/pickup`: не падай, пропусти перенос спеки, остальные шаги
выполни как обычно, и отметь это в отчёте.

## Замена шага 3 — lossy-правило по комментариям issue

```bash
gh issue view <N> -R <repo> --comments
```

Прочитай описание и все комментарии. Найди факты, которые кто-то будет
переиспользовать: решения, ограничения, изменения объёма, уточнения критериев
приёмки — и которых ещё нет ни в спеке, ни в `context/<слой>/invariants.md`,
ни в `context/<слой>/log.md`.

**Это не автоматическое действие.** Выпиши пользователю список кандидатов, по
строке на факт, с предложением адресата:

- долгоживущее правило уровня слоя → `context/<слой>/invariants.md`
- дата и событие уровня слоя → `context/<слой>/log.md` (через `ledger:scribe`)
- решение уровня задачи → секция `## Decisions` спеки, до её переноса

Дождись решения пользователя и только потом пиши. Если кандидатов нет — скажи
об этом явно, молча шаг не пропускай.

## Замена шага 6 — закрытие issue

У `gh issue close` есть только `-c/--comment` со строкой — файла он не
принимает. Поэтому однострочная сводка идёт прямо в `--comment`, а
многострочная кладётся отдельным комментарием перед закрытием:

```bash
# однострочная сводка
gh issue close <N> -R <repo> --reason completed --comment "<сводка>"

# многострочная сводка
gh issue comment <N> -R <repo> --body-file <файл>
gh issue close <N> -R <repo> --reason completed
```

Затем сними метку прогресса — у GitHub Issues нет статусов, «In Progress»
выражается меткой `in-progress`:

```bash
gh issue edit <N> -R <repo> --remove-label in-progress
```

Если метки на issue не было (задача шла мимо `/pickup`), команда вернёт ошибку —
это не повод падать: отметь в отчёте и иди дальше.

Метки слоёв `layer:<name>` при закрытии не трогаются.

## Замена шага 7 — пуш с подтверждением

Оригинал пушит сразу; здесь — явная остановка. Покажи, что уйдёт в origin:

```bash
git rev-parse --abbrev-ref HEAD
git log --oneline origin/<branch>..HEAD   # или @{u}..HEAD, если апстрим есть
```

Выведи ветку и список коммитов и спроси простым текстом
**«Push to origin? (yes / no)»**. Только после явного «да»:

```bash
git push -u origin <current-branch>
```

Пуш необратим для чужих глаз, а проект приватный и однопользовательский —
цена подтверждения нулевая. При отказе скилл завершается, отчёт печатается,
строка `Pushed` помечается как пропущенная.

## Финальный отчёт

Форма оригинала, со строкой Tracker в GitHub-виде:

```
Context updated:  <файлы context/<слой>/log.md через запятую>
Lossy-rule check: <поднято N фактов | нечего поднимать>
Commit:           <короткий хеш> — <тема коммита>
Tracker:          #<N> → closed
Pushed:           origin/<branch>   (или: не пушили — отказ пользователя)
```

Больше ничего.

## Важно

- Скилл не создаёт issue — это `/capture`.
- Не мержит ветку и не удаляет её — это делает человек.
- Не трогает `docs/decisions/` — архитектурные решения заводит `/adr`.
- Не запускает деструктивных git-команд: ни `reset --hard`, ни `checkout --`,
  ни `clean -f`.
- Не пушит без подтверждения и не пушит в дефолтную ветку: если текущая ветка
  дефолтная — предупреди и остановись до пуша.
- Не пропускает хуки (`--no-verify`) и не делает `--force`.
