# capture (GitHub)

Обёртка над плагинным `ledger:capture`. Поведение оригинала сохраняется целиком;
заменяются только шаги, которые ходят в трекер — вместо Linear используется
`gh` и GitHub Issues.

## Как читать оригинал

Найди оригинальный SKILL.md динамически, версию не хардкодь:

```bash
ls -d ~/.claude/plugins/cache/ledgerloop/ledger/*/skills/capture/SKILL.md | sort -V | tail -1
```

Если команда ничего не вернула — скажи пользователю, что плагин `ledger` не
установлен, и остановись. Иначе прочитай найденный файл и следуй ему дословно:
решение trivial/non-trivial, шаблон issue, шаблон спеки, бюджет
`budgets.specLines`, правила slug, делегирование черновика спеки агенту
`ledger:scribe`, подтверждение перед созданием. Ниже — только замены.

## Проверка окружения

Перед первым сетевым вызовом выполни `gh auth status`. Если gh не
авторизован — скажи об этом прямо (`gh auth login`) и остановись, ничего не
создавая.

Репозиторий вычисляй при каждом запуске из `ledgerloop.config.json`:
`<tracker.team>/<tracker.project>` (сейчас `ArghTeam/razdacha`). Не хардкодь.
Все вызовы `gh` — с явным `-R <repo>`.

## Замена шага 3 — поиск существующего issue

```bash
gh issue list -R <repo> --state open --search "<ключевые слова>"
```

Если по открытым ничего не нашлось, а работа выглядит как возврат к старой
теме — повтори с `--state all`. Покажи совпадения и спроси: новый issue или
обновить существующий?

## Замена шага 7 — создание

1. Тело issue запиши во временный файл (скратчпад или `/tmp`) — оно
   многострочное и на русском, в аргумент его класть нельзя.
2. Метки слоёв: по одной `layer:<name>` на каждый слой из секции
   «Domains touched» черновика спеки; имена слоёв берутся из `layers[].name`
   конфига, не выдумываются. Если метки в репозитории нет — создай:

   ```bash
   gh label create "layer:<name>" -R <repo> --description "<описание слоя из конфига>" --force
   ```

   `--force` обновляет уже существующую метку вместо ошибки, поэтому шаг
   идемпотентен. Не глуши вывод через `|| true`: так молча проглатывается и
   отказ по правам, и скилл пойдёт дальше с непроставленной меткой.
3. Создай issue:

   ```bash
   gh issue create -R <repo> \
     --title "<title>" \
     --body-file <файл> \
     --assignee @me \
     --label "layer:<name>" [--label "layer:<name2>" ...]
   ```
4. Из вывода `gh issue create` возьми URL; номер — хвост URL после последнего
   `/`.

У GitHub Issues нет статусов: «In Progress» здесь выражается меткой
`in-progress`. `/capture` её не ставит — это делает `/pickup`.

## Замена шага 5/7 — спека

Путь: `tasks/<N>-<slug>.md`, где `<N>` — номер issue без решётки, `<slug>` —
по правилам оригинала.

Во фронтматтере номер **обязательно в кавычках**:

```
---
type: spec
tracker: "#12"
---
```

Без кавычек YAML прочитает `#` как начало комментария и поле окажется пустым.
В черновике до создания issue оставляй `tracker: "<pending>"`.

## Подтверждение

Сохраняется как в оригинале и не пропускается: покажи черновик issue (и спеки,
если она есть) в fenced-блоках и спроси простым текстом
**«Create this? (yes / edit / cancel)»**. Интерактивную форму не строй.
До явного «да» не создаются ни issue, ни метки, ни файл спеки.

## Финальный отчёт

По строке на пункт:

- issue: `#<N>` — `<URL>`
- спека: `tasks/<N>-<slug>.md` (или «не заводилась — работа тривиальная»)
- метки: `layer:<...>, layer:<...>`

## Важно

- Скилл не закрывает и не комментирует issue — это `/close`.
- Не ставит метку `in-progress` и не создаёт ветку — это `/pickup`.
- Не делает `git commit`, `git push` и никаких деструктивных git-команд.
- Не трогает `docs/decisions/` — архитектурные решения заводит `/adr`.
- Не изобретает слои: список слоёв — только `layers[].name` из
  `ledgerloop.config.json`.
