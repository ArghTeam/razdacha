# 0002. Исходящие WireGuard-туннели в userspace sing-box

Дата: 2026-07-25 · Статус: принято

## Контекст

Один из типов исходящего туннеля — WireGuard (например, туннель к арендованному
зарубежному серверу). Реализовать можно двумя способами.

**Kernel-интерфейс.** Поднять `wg1`, `wg2`… средствами ядра, а в sing-box создать
`direct`-outbound с `bind_interface`. Так делает Podkop через `connection_type = vpn`.

**Userspace.** Использовать встроенную в sing-box реализацию WireGuard — секция
`endpoints` (с версии 1.11). Отдельного сетевого интерфейса не существует.

## Решение

**Userspace, через `endpoints` sing-box.** Требуемая версия sing-box — ≥ 1.12.0.

Следствие для модели данных: **любой туннель — это один outbound либо endpoint в конфиге
sing-box**, независимо от протокола. Единообразие.

## Последствия

**Положительные**

- Нет N сетевых интерфейсов, N таблиц маршрутизации и правил их разведения.
- **Петли невозможны по построению.** Трафик к апстрим-эндпоинту исходит от процесса
  sing-box, а первое правило цепочки `mangle` — `iifname != "wg0" return` — отсекает всё,
  что пришло не от клиентов. При kernel-интерфейсах пришлось бы явно исключать адреса
  эндпоинтов из заворачивания.
- Добавление туннеля любого типа — одна операция в UI и одна вставка в JSON. Это то,
  что делает экран «Туннели» простым.
- Состояние целиком в конфиге sing-box: нет расхождения между тем, что в БД, и тем, что
  в сетевых настройках ядра.

**Отрицательные**

- Шифрование в userspace медленнее kernel-реализации. Для VPS с 1–2 vCPU потолок
  оценивается сотнями Мбит/с — для целевого сценария (1–20 личных клиентов) достаточно,
  но это ограничение, а не отсутствие ограничения.
- Жёсткая зависимость от sing-box ≥ 1.12.0.
- **AmneziaWG не поддерживается.** sing-box не реализует awg. Если он понадобится —
  отдельный тип туннеля через kernel-модуль `amneziawg-tools` и `bind_interface`, то есть
  возврат к первому варианту для одного протокола. Не в первых версиях.

## Альтернативы

**Kernel-интерфейсы (как в Podkop).** Отклонено: выигрыш в производительности не
окупает сложности разведения маршрутов и риска петель. На роутере с OpenWrt выбор
оправдан — там процессор слабый и каждый процент важен; на VPS соотношение другое.

## Источник в Podkop

`podkop/files/usr/bin/podkop:722` — ветка `connection_type = vpn`;
`sing_box_config_manager.sh:914` — `sing_box_cm_add_interface_outbound`, реализующая
`type: direct` + `bind_interface`. Именно этот подход мы **не** повторяем.

Отмечено при разборе: в `podkop:741` эта ветка использует глобальный `$dns_server` вместо
`$domain_resolver_dns_server` секции — ещё один аргумент против ручного связывания
интерфейсов.
