# 0005. IPv6 отключён, основной механизм — DNS

Дата: 2026-07-25 · Статус: принято

## Контекст

Поддержка IPv6 удваивает поверхность: вторые наборы nft-правил, второй диапазон FakeIP,
двойные списки подсетей, двойная маршрутизация. При этом неполная поддержка хуже
отсутствующей — она даёт утечки, при которых часть трафика идёт мимо туннеля незаметно
для пользователя.

## Решение

IPv6 для клиентов отключён полностью, тремя слоями.

**Слой 1 — DNS, основной.** В sing-box `"strategy": "ipv4_only"`. Клиенту никогда не
приходят AAAA-записи, поэтому приложения не пытаются идти по IPv6. Работает в источнике,
до всякого firewall, и закрывает подавляющее большинство случаев. FakeIP объявляется
только для v4 (`inet4_range`, без `inet6_range`).

Это возможно только потому, что мы владеем резолвером клиента целиком
([ADR 0001](0001-gateway-not-desktop.md)).

**Слой 2 — маршрутизация.** `AllowedIPs` содержит `::/0`, но IPv6-адрес пиру не выдаётся.
Неочевидно, но обязательно: с одним лишь `0.0.0.0/0` v6-трафик на литеральные адреса
уходит **мимо туннеля**, через локальную сеть клиента — прямая утечка. С `::/0` он
затягивается в туннель и умирает там.

**Слой 3 — nftables.** `reject with icmpv6 type admin-prohibited` для `iifname "wg0"`.
Именно reject, не drop: браузеры используют Happy Eyeballs — пробуют v6 и через ~250 мс
параллельно v4. Молчаливый drop даёт четверть секунды задержки на каждое соединение;
reject — мгновенный отказ и немедленный переход на IPv4.

**Чего не делаем:** `net.ipv6.conf.all.disable_ipv6=1` на сервере. Глушим IPv6 только для
клиентов. Самому серверу он может быть нужен — часть VPS-провайдеров использует его для
управления, отдельные апстрим-прокси доступнее по v6.

## Последствия

**Положительные**

- Одна версия протокола во всей системе: один набор nft-правил, один диапазон FakeIP,
  одна ветка в генераторе конфига.
- Утечки IPv6 невозможны — это самый частый дефект самодельных VPN-сетапов.
- Отказ мгновенный, пользователь не замечает задержек.

**Отрицательные**

- IPv6-only ресурсы недоступны. Таких единицы; факт документируется явно.
- Клиенты в сетях, где провайдер даёт только IPv6 с NAT64/DNS64, могут вести себя
  непредсказуемо — сам туннель к серверу поднимется (`Endpoint` по v4 через NAT64),
  но сценарий не тестируется.
- Решение придётся пересматривать, если доля IPv6-only ресурсов вырастет.

## Альтернативы

**Полная поддержка IPv6.** Отклонено: удвоение сложности при почти нулевой пользе для
целевого сценария.

**Только слой 3 (блокировка на firewall).** Отклонено: даёт задержки Happy Eyeballs
на каждое соединение и не спасает от утечек, если клиент не маршрутизирует `::/0`
в туннель.

**Только слой 1 (DNS).** Отклонено: не покрывает обращения по литеральным адресам.

## Источник в Podkop

`sing_box_config_manager.sh:62` — `sing_box_cm_configure_dns` со `strategy=ipv4_only`;
`:221` — `sing_box_cm_add_fakeip_dns_server` с `inet4_range=198.18.0.0/15` без v6.
Podkop приходит к тому же выводу, но не документирует его и не закрывает утечку на
уровне маршрутизации — у него нет клиентских конфигов, где это можно было бы сделать.
