# 0010. Туннель-пул: N outbound'ов и `urltest` под тегом туннеля

Дата: 2026-07-26 · Статус: принято · Уточняет [0003](0003-tunnel-separate-from-rule.md)

## Контекст

Бесплатные VLESS-ключи живут недолго. Каталог вроде `vpnkeys.me/protocol/vless` отдаёт
больше сотни ключей, из которых в любой момент работает часть, и какая именно — заранее
неизвестно. Туннель, заведённый по одному такому ключу, умирает молча: правило на месте,
конфиг валиден, трафик никуда не идёт.

Решение [0003](0003-tunnel-separate-from-rule.md) описывает туннель как «ровно один
outbound либо endpoint» и уже тогда упоминало путь к failover — `urltest`-группу sing-box.
Оно же оставило вопрос открытым: правило ссылается на туннель одним `tunnel_id`, а группа
из ста серверов — это сто outbound'ов, и как их достать из одной ссылки, не переписывая
модель правил, было неясно.

Второе обстоятельство обнаружилось чтением своего же кода применения конфига:

- `internal/singbox/apply_exec.go:60` перезагружает сервис через
  `systemctl reload-or-restart`. У штатного юнита sing-box нет `ExecReload`, поэтому это
  **перезапуск процесса**: рвутся соединения через **все** туннели, а не только через тот,
  который менялся.
- `internal/singbox/apply.go:202` `sameOnDisk` — единственная защита от такого
  перезапуска. Она срабатывает только при **байт-в-байт** совпадении нового конфига с
  лежащим на диске.

Значит цена смены сервера внутри пула и цена обновления каталога — разные величины, и
разводить их надо в коде, а не в намерениях.

## Решение

**Пул — форма туннеля, не новая сущность.** В БД это тот же `tunnels`: `source = pool`,
`raw` — URL каталога, плюс снятый со страницы список серверов и время обновления. Правило
по-прежнему ссылается на туннель одним `tunnel_id` — модель правил не меняется.

**В конфиге за одним тегом стоит группа.** Включённый пул разворачивается в N outbound'ов
типа `vless` с производными тегами (`tun-<id>-0`, `tun-<id>-1`, …) плюс один outbound типа
`urltest`, чей тег — `TunnelTag(t.ID)`, то есть ровно тот, на который ссылаются правила.
Снаружи туннель остаётся одним тегом; это и есть уточнение 0003: «ровно один outbound»
превращается в «ровно один тег, на который ссылаются правила».

**Health-check и переключение отдаёт sing-box.** `urltest` сам пробует участников по
своему интервалу и уводит трафик с мёртвого. Смена сервера не трогает ни конфиг на диске,
ни правила, ни соседние туннели, ни процесс sing-box.

**Серверы сериализуются в детерминированном порядке.** Отбор из каталога — по пингу из
карточки, сериализация отобранного — по возрастанию URL. Неизменившийся набор обязан давать
байт-в-байт тот же JSON, иначе `sameOnDisk` не совпадает и sing-box перезапускается на
каждом обновлении каталога — с разрывом соединений во всех остальных туннелях.

**Два интервала, разведённые по цене.**

| Что | Значение | Почему |
|---|---|---|
| `urltest.interval` — ротация внутри пула | 3 минуты | бесплатно: пробы внутри процесса, конфиг не меняется, соседи не страдают |
| обновление каталога | 12 часов | дорого: изменившийся набор переписывает конфиг и перезапускает sing-box. Сайт сам объявляет `profile-update-interval: 12` |

**Число серверов в конфиге ограничено.** Полнота пула не требуется — нужно несколько
работающих ключей, а не все 127. В конфиг идут лучшие по пингу карточки; остальные лежат в
БД и всплывут при следующем отборе.

**Пустой пул пропускается, а не роняет генерацию.** Пул, из которого не разобрался ни один
сервер, выпадает из конфига вместе со ссылающимися на него правилами — как выключенный
туннель. Ошибка здесь заморозила бы весь конфиг, включая исправные туннели, из-за чужого
недоступного сайта.

## Последствия

**Положительные**

- Мёртвый сервер выводится из работы без участия демона: ни записи в БД, ни перезаписи
  конфига, ни перезапуска.
- Соседние туннели переживают ротацию: перезапуск случается только при изменившемся наборе
  серверов, то есть раз в 12 часов и не всегда.
- Модель правил не тронута: правило видит один тег, как и раньше.
- Ограничение по пингу даёт побочный выигрыш — конфиг остаётся читаемым руками.

**Отрицательные**

- Конфиг распухает: один пул — это N+1 записей в `outbounds[]` вместо одной. Отсюда и
  потолок.
- Диагностика усложняется: «туннель работает» теперь значит «работает хотя бы один
  участник группы», и панели придётся показывать состав, а не одну лампочку.
- Пробы `urltest` идут с сервера постоянно, даже когда через туннель никто не ходит.
  Смягчается `idle_timeout`: простаивающая группа перестаёт проверяться.
- Появляется зависимость от разметки чужой страницы. Разметка server-side, её правка
  ломает разбор молча — отсюда обязательная фикстура страницы в тестах.
- `reload-or-restart` остаётся перезапуском. Пул делает это заметнее, но не создаёт: смена
  правила стоит ровно столько же. Отдельная задача — не эта.

## Альтернативы

**Подмена конфига по таймеру.** Демон сам проверяет серверы и вписывает живой в единственный
outbound. Отвергнуто: каждая смена сервера — перезапись конфига и перезапуск sing-box,
то есть разрыв соединений во всех туннелях ради починки одного. Health-check пришлось бы
писать самим, а он уже есть в sing-box.

**`selector` вместо `urltest`.** Ручной выбор участника через Clash API. Отвергнуто:
выбирать пришлось бы по своему health-check, то есть та же работа плюс состояние вне БД.
`selector` пригодится, когда пользователь захочет прибить туннель к конкретной стране.

**Пул как отдельная сущность рядом с туннелем.** Отвергнуто: `Rule.tunnel_id` пришлось бы
превратить в ссылку на одно из двух, а UI — в развилку. Пул отличается от туннеля способом
получения конфига, и это `source`, ровно как `url` против `wg_conf`.

**Все 127 ключей в конфиг.** Отвергнуто: 127 записей в `outbounds[]` и 127 проб каждые три
минуты ради результата, который дают десять.
