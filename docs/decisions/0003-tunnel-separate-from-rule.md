# 0003. Туннель и правило — разные сущности

Дата: 2026-07-25 · Статус: принято

## Контекст

Podkop использует одну сущность — секцию `config section 'main'`, которая содержит
одновременно конфигурацию подключения (`proxy_config_type`, `proxy_string`,
`outbound_json`) и списки маршрутизации (`community_lists`, `user_domains`,
`user_subnets`, `remote_domain_lists`). Одна секция = один прокси + его списки.

Для роутера с одним-двумя каналами это работает. Для сервера с несколькими исходящими
туннелями возникают вопросы: как направить два разных набора списков в один туннель, не
дублируя его конфигурацию? как переключить группу списков на резервный туннель одним
действием?

## Решение

Две отдельные сущности:

- **Tunnel** — только «куда»: тип, конфигурация подключения, статус, latency.
- **Rule** — только «что и в каком порядке»: списки, приоритет, действие
  (`tunnel` / `direct` / `block`), ссылка на туннель, область действия по клиентам.

Связь — `Rule.tunnel_id → Tunnel.id`, многие-к-одному.

## Последствия

**Положительные**

- Один туннель переиспользуется несколькими правилами без дублирования конфигурации.
- Переключение набора списков на другой туннель — смена одного поля, а не
  перенастройка секции.
- Открывается путь к failover: несколько туннелей под одним правилом через
  `urltest`-группу sing-box (не в первой версии, но модель не мешает).
- UI распадается на два простых экрана вместо одного сложного. Форма добавления туннеля
  содержит два поля; форма правила не спрашивает про протоколы.
- Статус и latency естественно принадлежат туннелю и показываются один раз, а не в
  каждой секции.

**Отрицательные**

- Сущностей на одну больше, добавление первого правила требует двух шагов
  (сначала туннель, потом правило). Смягчается тем, что установщик может создать
  правило-заготовку.
- Удаление туннеля требует проверки ссылок — `ON DELETE RESTRICT` с внятным
  сообщением вместо каскада.

## Дополнительно: явный приоритет

Правила маршрутизации sing-box проверяются по порядку, первое совпадение выигрывает.
Podkop порядок секций не выставляет, и при пересекающихся списках результат неочевиден —
это скрытый источник багов, которые тяжело диагностировать.

Поэтому `Rule.priority` — обязательное поле, видимое в UI перетаскиванием, с подписью
«проверяются сверху вниз» прямо в шапке списка. Это единственная концепция, которую
пользователь обязан понять.

## Источник в Podkop

`podkop/files/etc/config/podkop` — схема секции `main`;
`podkop/files/usr/bin/podkop:622` (`configure_outbound_handler`) и `:912`
(`configure_routing_for_section_lists`) — обработка обеих ролей одной секции.
