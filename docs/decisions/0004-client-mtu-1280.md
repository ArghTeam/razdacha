# 0004. MTU клиентов 1280

Дата: 2026-07-25 · Статус: принято

## Контекст

Накладные расходы WireGuard — 60 байт при IPv4-эндпоинте (20 IP + 8 UDP + 16 заголовок
+ 16 тег Poly1305) или 80 при IPv6. При пути 1500 максимум — 1440 или 1420
соответственно; дефолт `wg-quick` = 1420 выбран по второму варианту.

Но у нас двойная инкапсуляция, и она ведёт себя по-разному:

- **TCP через sing-box MTU-цепочки не образует.** tproxy терминирует соединение и
  открывает новое; два независимых сегмента со своими MSS. Прощает почти любой MTU.
- **UDP образует.** Датаграмма форвардится целиком; при выходе через
  userspace-WireGuard сверху ложится 28 байт внутреннего IP+UDP плюс 60 внешнего wg —
  **+88 байт**. Это QUIC, то есть YouTube и Google.
- **Прямой путь (masquerade) образует и наиболее уязвим.** Обратный трафик приходит
  пакетами по 1500 и должен быть вложен в `wg0` с меньшим MTU. Работает только через
  PMTUD, а ICMP «Fragmentation Needed» режут повсеместно → чёрная дыра: мелкие страницы
  открываются, крупные висят.

Целевой пользователь сканирует QR-код и не знает слова MTU.

## Решение

`client_mtu = 1280` по умолчанию, прописывается в генерируемые клиентские конфиги.
MTU интерфейса `wg0` на сервере — то же значение.

Дополнительно — MSS-клампинг в цепочке forward в обе стороны, несмотря на фиксированный
MTU.

## Обоснование значения

1280 — минимальный MTU IPv6, гарантированно проходящий любой маршрут в интернете.
Tailscale и Cloudflare WARP выбрали это же значение.

Запас от теоретического максимума — 160 байт. Одновременно покрывает PPPoE (1492),
сервер за чужим туннелем, мобильных операторов с нестандартным MTU и двойную
инкапсуляцию UDP.

**Цена.** Полезная нагрузка 1240 из 1340 байт на проводе против 1380 из 1480 при
MTU 1420 — разница в эффективности менее 1%. Один тикет «не открывается сайт» стоит
дороже.

## Последствия

- Целый класс жалоб («сайт грузится наполовину», «видео не играет», «загрузка файла
  обрывается») исчезает до первого пользователя.
- Потеря пропускной способности менее 1%.
- MTU остаётся настраиваемым в UI с подсказкой «1420 для максимальной скорости в
  надёжной сети» — для тех, кто понимает, что делает. Настройка глобальная, не
  per-client: per-client MTU — ровно та перегруженность интерфейса, которой продукт
  избегает.
- Изменение значения требует перевыпуска клиентских конфигов; API отвечает
  `requires_client_reconfig: true`.

## Почему клампинг всё равно нужен

Прежде всего ради прямого пути: заставляет удалённые серверы присылать сегменты ≤ 1240,
так что фрагментация не требуется и PMTUD не участвует. Плюс страховка от клиентов,
игнорирующих `MTU` из конфига (встречается в старых Android-реализациях).

ICMP type 3 code 4 не блокируется — PMTUD остаётся вторым эшелоном.

## Источник в Podkop

Отсутствует. Podkop работает на роутере, где клиентские устройства подключены по
Ethernet/Wi-Fi с MTU 1500 и двойной инкапсуляции на клиентском плече нет. Это первое
существенное расхождение архитектур.
