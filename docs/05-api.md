# API

REST поверх HTTP. Демон слушает `127.0.0.1:8080`, снаружи
его закрывает nginx ([ADR 0008](decisions/0008-nginx-before-panel.md)). Панель доступна
из интернета, поэтому доступ закрыт паролем и сессией
([ADR 0009](decisions/0009-public-panel-access.md)); TLS терминируется на nginx, до
демона доходит обычный HTTP по loopback.

Все ответы — JSON. Ошибки: `{"error": "человекочитаемое сообщение", "code": "slug"}`
с соответствующим HTTP-статусом. Сообщения на русском, они показываются пользователю
как есть.

## Auth

| Метод | Путь | Описание |
|---|---|---|
| `POST` | `/api/login` | `{password}` → cookie сессии |
| `POST` | `/api/logout` | удалить сессию и погасить cookie |
| `GET` | `/api/session` | `{authenticated, expires_at}` |

Всё под `/api/`, кроме `/api/login`, требует действующей сессии; без неё — `401` с
кодом `unauthorized`. Неверный пароль — тоже `401`: отличать «нет сессии» от «пароль не
тот» на стороне протокола незачем, UI различает их по тому, какой запрос он послал.

Сессия живёт в cookie `razdacha_session` (`HttpOnly`, `Secure`, `SameSite=Lax`, срок
сутки, продление на второй половине срока). В БД лежит хеш токена, а не сам токен.
Пароль хранится хешем argon2id; демон не стартует, пока пароль не задан.

Серия неудачных попыток с одного адреса блокирует вход на этот адрес: `429`, код
`too_many_attempts`, заголовок `Retry-After`. Успешный вход счётчик сбрасывает. Адрес
берётся из `X-Real-IP`/`X-Forwarded-For`, но **только** если запрос пришёл с loopback,
то есть от нашего nginx; иначе — адрес соединения.

## Peers

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/api/peers` | список с живой статистикой |
| `POST` | `/api/peers` | создать; тело `{name}`, ключи и адрес генерируются |
| `PATCH` | `/api/peers/{id}` | `{name?, enabled?}` |
| `DELETE` | `/api/peers/{id}` | удалить пира и его ссылки в правилах |
| `GET` | `/api/peers/{id}/config` | клиентский `.conf`, `text/plain` |

```jsonc
// GET /api/peers
[{
  "id": "...", "name": "iPhone Ромы", "address": "10.8.0.5",
  "public_key": "…", "created_at": "2026-06-14T10:00:00Z",
  "enabled": true, "online": true,
  "last_handshake": "2026-07-25T12:03:11Z",
  "rx_bytes": 184320000, "tx_bytes": 12800000,
  "endpoint": "203.0.113.44:41233"
}]
```

Приватный и pre-shared ключи в списке не отдаются: наружу они уходят один раз и
целиком — в клиентском конфиге.

**Производные поля (`online`, `last_handshake`, `rx_bytes`, `tx_bytes`, `endpoint` у
пира; `status`, `latency_ms`, `last_check` у туннеля) — `null`, пока их некому
заполнить.** Источник у них один — слой netstack и клиент Clash API; ноль означал бы
измеренный ноль, а `"down"` — утверждение о туннеле, которого никто не проверял.

**QR-код рисует клиент, а не сервер.** Отдельного `/api/peers/{id}/qr` нет: конфиг —
это текст, кодер помещается в UI (`ui/prototype/app.js`), и картинка с сервера
означала бы генератор PNG в демоне ради того, что уже нарисовано в браузере.

**Производные поля туннеля заполняет расписание, а не только кнопка «Проверить».**
Демон снимает состояние каждые `tunnel_check_interval`, одним запросом `/proxies` к
Clash API; статус и время переживают перезапуск, задержка — нет. Поэтому `null` в
`status` означает «ещё ни разу не проверялся», а не «проверка не запускалась»
([ADR 0011](decisions/0011-tunnel-check-schedule.md)).

`GET /api/peers/{id}/config` отвечает `503` с кодом `not_ready`, пока не известен
публичный ключ сервера или `endpoint_host`: конфиг без них выглядит рабочим, но не
подключается.

**Имя файла строит демон и присылает в `Content-Disposition`.** Клиент WireGuard для
Android берёт из него имя туннеля и валидирует как `[a-zA-Z0-9_=+.-]{1,15}`, поэтому
имя пира транслитерируется и режется по этому пределу; префикса у имени нет — он
съедал бы больше половины бюджета. UI своё имя не строит: второй слагификатор давал
бы для одного пира разные файлы в зависимости от того, скачали через панель или
дёрнули эндпоинт.

## Tunnels

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/api/tunnels` | список со статусом и latency |
| `POST` | `/api/tunnels` | `{name, raw}` — тип определяется автоматически; ссылка на каталог ключей — `409` |
| `PATCH` | `/api/tunnels/{id}` | `{name?, raw?, enabled?}` |
| `DELETE` | `/api/tunnels/{id}` | `409`, если на туннель ссылается правило или он встроенный |
| `POST` | `/api/tunnels/parse` | разбор без сохранения — для превью в форме |
| `POST` | `/api/tunnels/warp` | `{name?}` — зарегистрировать устройство WARP и завести туннель |
| `POST` | `/api/tunnels/{id}/check` | измерить latency сейчас |
| `POST` | `/api/tunnels/{id}/refresh` | обойти каталог туннеля-пула сейчас |
| `GET` | `/api/tunnels/{id}/pool` | серверы туннеля-пула по одному |

В каждом туннеле есть флаг `builtin`: `true` означает запись, которую завёл сам демон
(сейчас это пул бесплатных ключей, и он единственный). Такую запись нельзя удалить —
только выключить, — и панель по этому флагу собирает ей своё меню. Всё остальное у неё
как у обычного туннеля.

`POST /api/tunnels/parse` возвращает `{type, host, port, security, transport, warnings[]}`
либо `400` с указанием, что именно в строке не разобралось. Форма показывает результат
до сохранения, чтобы пользователь видел, что вставил не то.

`POST /api/tunnels/{id}/check` спрашивает работающий sing-box по Clash API и отвечает
`{id, status, latency_ms, last_check, detail}`. Статусы: `up` — задержка измерена,
`down` — sing-box проверил и до цели не дошёл, `not_applied` — туннеля нет в
работающем конфиге (создан или выключен, но не применён). Не отвечает сам sing-box —
`503` с кодом `not_ready`: о туннеле при этом ничего не известно, и «down» был бы
выдумкой. Результат последней проверки живёт в памяти демона и оттуда попадает в
производные поля `GET /api/tunnels`; после перезапуска они снова `null`.

### WARP

`POST /api/tunnels/warp` регистрирует у Cloudflare бесплатное устройство и заводит из
его ключей обычный WireGuard-туннель: `type = wireguard`, `source = warp`. Ответ — сам
туннель, код `201`. Имя по умолчанию — «WARP», своё передаётся полем `name`.

Это **единственное** место, откуда демон ходит в Cloudflare: ни старт, ни миграция, ни
расписание туда не заглядывают — тот же контракт, что у туннеля-пула
([ADR 0010](decisions/0010-tunnel-pool-urltest.md)). Внешних бинарников в цепочке нет:
`wgcf` не тянем, ключи генерируются на месте, наружу уходит только публичная половина.

WARP в системе один: туннель с `source = warp` уже есть — `409` с кодом `conflict`, и
запроса наружу при этом не происходит вовсе, чтобы повторное нажатие не оставляло у
Cloudflare лишних устройств. Тот же `409` приходит, если WARP завели вставкой `.conf`
руками: такой конфиг получает `source = warp` сам, по хосту endpoint в домене
`cloudflareclient.com` ([ADR 0012](decisions/0012-tunnel-chain-detour.md)).

Отказы разведены, потому что чинятся по-разному: не дозвонились — `502` с текстом про
связь с Cloudflare, ответил отказом — `502` с текстом про отказ и предложением повторить
позже. При обоих туннель не создаётся. Конфиг здесь не применяется — как и у остальных
правок туннелей, это отдельный `POST /api/apply`.

### Туннель-пул

Пул в системе один, и он встроенный: его заводит демон (см. ниже), а `POST /api/tunnels`
со ссылкой `http(s)://` на каталог ключей отвечает `409` с кодом `conflict` и текстом про
то, что пул уже есть и его достаточно включить. Своих пулов пользователь не создаёт —
второй пул означал бы второй обход того же каталога и вторую группу `urltest` в конфиге
без всякой пользы.

Разбор ссылки на каталог при этом остался: `POST /api/tunnels/parse` показывает такой ввод
как пул — без адреса и шифра, их ещё нет, — и им же пользуется заведение встроенного пула.
Форма ссылки проверяется до отказа, поэтому битая ссылка получает свои `400` с объяснением,
а не общий отказ.

У пула (`source = pool`, `type = vless` — см. ADR 0010) в ответе есть блок `pool`;
у остальных туннелей его нет. Тип остаётся протоколом: пул из vless-серверов — это
vless, а «пул» — это форма конфига, и интерфейс узнаёт его по `source`.

```json
"pool": {
  "catalog_url": "https://vpnkeys.me/protocol/vless",
  "servers_total": 24,
  "servers_alive": 19,
  "current": {"name": "VLESS (Netherlands) 8821", "country": "Netherlands", "latency_ms": 210},
  "updated_at": "2026-07-26T03:52:00Z",
  "next_update_at": "2026-07-26T15:52:00Z"
}
```

`servers_total` и время обхода читаются из БД. `servers_total` — это размер известного
списка, а не размер каталога: список копит серверы между обходами и выбрасывает сервер
только после трёх пропусков подряд (issue #68), поэтому он обычно больше того, что каталог
отдаёт за один раз. Панель так и подписывает — «известно N серверов», а не «в каталоге».
`servers_alive` и `current` берутся из
Clash API: живых считает сам `urltest`, по которому и идёт ротация, а вторая
собственная проверялка расходилась бы с ней. Оба поля `null`, если sing-box недоступен
или пул выключен — ноль живых был бы утверждением о пуле, которого никто не спрашивал,
а цифры у выключенного туннеля — ложь. Недоступный Clash API не роняет список: остальные
туннели отдаются как обычно.

`POST /api/tunnels/{id}/refresh` обходит каталог и обновляет состав серверов в БД.
Конфиг здесь не применяется — как и у остальных правок туннелей, это отдельный
`POST /api/apply`. У обычного туннеля — `400`, без поднятого расписания пулов — `503`
с кодом `not_ready`. Ответ — сам туннель вместе с блоком `pool`, чтобы карточке не
пришлось делать второй запрос за списком.

Обход по требованию не ждёт расписания: пул ручка уже прочитала из БД и передаёт его
расписанию целиком, а не по идентификатору. Раньше расписание искало пул в своём наборе,
который сверяется с БД раз в полминуты, и на свежем пуле ручка отвечала `404 «Туннель не
найден»` — неправдой дважды: туннель существовал, а причина отказа была временной
(issue #74).

### Встроенный пул

Пул бесплатных ключей демон заводит сам при первом запуске — выключенным, по каталогу
`lists.DefaultPoolCatalogURL`. У него `builtin: true`, и он в системе единственный.
Повторный старт второго пула не создаёт; если пул в БД уже есть (например, был заведён
руками до того, как пулы стали встроенными), демон помечает встроенным его, а не заводит
рядом второй. Оказалось пулов несколько — встроенным становится один (самый старый),
остальные остаются обычными туннелями и работают как работали; выбор уходит в лог.

`DELETE /api/tunnels/{id}` на встроенном отвечает `409` с кодом `conflict` и текстом про
то, что встроенный пул выключают, а не удаляют: прятать кнопку в панели, оставляя
разрешение в API, значит расходиться с самим собой. Остальные методы работают как обычно —
включение и выключение идёт штатным `PATCH {enabled}`, и `PATCH` флаг `builtin` не снимает,
иначе запрет на удаление обходился бы правкой.

### Серверы пула

`GET /api/tunnels/{id}/pool` отдаёт состав каталога по одному серверу. Отдельной ручкой, а
не полем в `GET /api/tunnels`: каталог — это сотня с лишним записей, и возить их в каждом
ответе экрана «Туннели» незачем. У обычного туннеля — `400`.

```json
{
  "catalog_url": "https://vpnkeys.me/protocol/vless",
  "updated_at": "2026-07-26T13:37:08Z",
  "servers": [
    {"title": "VLESS (Germany) 11293", "country": "Germany", "ping_ms": 36,
     "in_rotation": true, "alive": true, "latency_ms": 36, "current": true}
  ]
}
```

`title`, `country` и `ping_ms` — то, что было на карточке каталога; `ping_ms` равен `0`,
если карточка его не показала. `in_rotation` — попал ли сервер в конфиг: там лежат лучшие
по пингу карточки, но не больше `poolMaxServers` ([ADR 0010](decisions/0010-tunnel-pool-urltest.md)).

`alive` и `latency_ms` берутся из Clash API и осмысленны только для серверов в ротации —
у остальных они **строго `null`**: их никто не проверял, а `false` был бы утверждением о
непроверенном сервере, а `0` — «ноль миллисекунд». Те же `null` приходят на всю ротацию,
когда пул выключен или sing-box недоступен. `current` — сервер, который `urltest` выбрал
прямо сейчас; когда выбора нет, он `false` у всех.

Ссылки `vless://` наружу не отдаются: в них UUID ключа, а на экране от него пользы нет.
Порядок серверов — ротация впереди (по задержке, потом по пингу карточки), затем остальные
по стране и пингу; панель группирует их сама.

## Rules

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/api/rules` | по возрастанию `priority` |
| `POST` | `/api/rules` | создать; `priority` — в конец |
| `PATCH` | `/api/rules/{id}` | частичное обновление |
| `DELETE` | `/api/rules/{id}` | |
| `PUT` | `/api/rules/order` | `{ids: [...]}` — новый порядок целиком |
| `GET` | `/api/lists/community` | доступные сервисы: `{key, title, has_domains, has_subnets}` |

Переупорядочивание отдельным эндпоинтом, а не через `PATCH` каждого правила: порядок
меняется целиком и атомарно, промежуточных состояний с дублирующимися приоритетами быть
не должно.

`via_tunnel_id` — второе звено цепи ([ADR 0012](decisions/0012-tunnel-chain-detour.md)).
Принимается только у правила с `action = tunnel` и только если это туннель с
`source = warp`: иначе `400` с объяснением на русском — до генерации конфига и
`sing-box check`. Пустая строка снимает второе звено.

## Settings

| Метод | Путь |
|---|---|
| `GET` | `/api/settings` |
| `PATCH` | `/api/settings` |

Изменение `wg_listen_port`, `wg_pool` или `client_mtu` требует переподключения клиентов —
ответ содержит `{"requires_client_reconfig": true}`, UI показывает предупреждение.
Тем же признаком помечается смена `endpoint_host` и `wg_server_address`: они тоже
записаны в выданных клиентских конфигах.

`PATCH` частичный: присланные поля перезаписываются, остальные остаются как были.
`list_update_interval` и `tunnel_check_interval` — в секундах: наносекунды
`time.Duration` это деталь Go, а не контракт.

**`server_public_key` — публичный ключ `wg0` — отдаётся здесь, полем только на чтение.**
Хранимой настройкой он не является (`PATCH` его игнорирует), но клиентскому конфигу
необходим, а другой сущности API, где ему место, нет. Пока интерфейс не поднят —
`null`: ключи сервера заводит слой netstack.

## Notify

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/api/notify` | настройки оповещений без токена |
| `PUT` | `/api/notify` | сохранить настройки |
| `POST` | `/api/notify/test` | отправить пробное сообщение |

Как подключить бота — [Оповещения](09-notifications.md).

**Токен бота из API не возвращается ни в каком виде.** В ответе вместо значения —
признак `token_set`; интерфейс по нему показывает «сохранён» вместо пустого поля. Токен
лежит в таблице `settings`, но вне `Settings`, как и хеш пароля: иначе он переписывался
бы из `PATCH /api/settings` и уезжал бы обратно в `GET /api/settings`.

**Пустой `token` в `PUT` означает «оставить прежний».** Поле-указатель отличает «не
прислали» от «прислали пустое»: сохранение галочки не должно стирать секрет, которого в
форме и не было.

**Включить оповещения без токена или чата нельзя** — `400`. Такая настройка выглядит
рабочей в интерфейсе и молча ничего не шлёт.

`POST /api/notify/test` работает и при выключенных оповещениях: проверять канал
приходится до того, как его включишь. Без токена или чата — `409 not_ready`. Это
единственный исходящий запрос к телеграму, который делает демон, и делает он его по
явному нажатию, а не сам.
| `GET` | `/api/logs?source=razdachad\|sing-box&lines=200` | последние строки |

```jsonc
// GET /api/diag
{
  "checks": [
    {"id": "wg",       "title": "WireGuard",        "status": "ok",
     "detail": "wg0 поднят, 3 пира, 2 онлайн"},
    {"id": "singbox",  "title": "sing-box",          "status": "ok",
     "detail": "1.12.4, запущен 4 ч назад"},
    {"id": "nft",      "title": "Правила nftables",  "status": "ok",
     "detail": "таблица razdacha, 1284 подсети в сете"},
    {"id": "tunnels",  "title": "Туннели",           "status": "warn",
     "detail": "«Нидерланды» не отвечает"},
    {"id": "lists",    "title": "Списки",            "status": "ok",
     "detail": "обновлены 3 ч назад"},
    {"id": "forward",  "title": "IP forwarding",     "status": "ok"},
    {"id": "mtu",      "title": "Path MTU",          "status": "ok",
     "detail": "1500 до всех туннелей"}
  ],
  "checked_at": "2026-07-25T12:00:00Z",
  "overall": "warn"
}
```

Статусы: `ok` | `warn` | `error` | `unknown`. `overall` — худший из вернувшихся; `unknown`
считается хуже `ok`, но лучше `warn`: это невыполненная проверка, а не поломка.
Проверка, источника которой ещё нет в коде, остаётся в списке со статусом `unknown` и
объяснением в `detail` — молча пропадать из сводки она не должна.

`checked_at` — когда проверки отработали, RFC 3339 в UTC. Панель показывает время
последней проверки по нему, а не по часам браузера: иначе снимок часовой давности
выглядел бы сделанным только что.

**Прогон по одной.** `POST /api/diag/run?check=<id>` выполняет одну проверку и
возвращает тот же объект с единственным элементом в `checks`; `overall` в этом случае
равен её статусу. Идентификаторы — те же `id`, что в сводке, порядок фиксирован:
`wg`, `singbox`, `nft`, `tunnels`, `lists`, `forward`, `mtu`. Неизвестный `id` — `400`
`bad_request`, а не пустой список: пустая сводка читалась бы как «проверять нечего».
Прогон одной проверки читает только нужные ей источники.

Эндпоинт разбит ради показа хода в панели: сводка одним ответом не даёт отличить
«проверка идёт» от «проверка закончилась», и экран диагностики семь секунд выглядел
замершим. Панель прогоняет проверки по очереди в перечисленном порядке, показывает
«проверяется» на ещё не ответивших строках и считает общий статус сама по тому же
правилу худшего. `POST /api/diag/run` без параметра остаётся и делает всё за один
запрос — им пользуются те, кому ход не нужен.

## Applying

| Метод | Путь | Описание |
|---|---|---|
| `POST` | `/api/apply` | пересобрать конфиг sing-box и nft, применить |
| `GET` | `/api/apply/status` | есть ли несохранённые изменения |

Изменения через REST пишутся в БД **сразу**, но применяются пакетно по `/api/apply`.
Причина: правка правил — многошаговая операция, и перегенерировать конфиг sing-box после
каждого нажатия дорого и вызывает разрывы соединений. UI показывает плашку «есть
непримененные изменения» с кнопкой.

Ошибка `sing-box check` возвращает `422` с текстом ошибки; предыдущий конфиг остаётся
активным.

## Живые данные

Отдельного канала нет: панель опрашивает REST раз в 15 секунд и перечитывает данные
экрана при заходе на него. Опрос стоит на паузе, пока вкладка скрыта или открыта
модалка.

WebSocket был обещан в первом наброске этой документации и не был написан: единственным
потребителем канала был бы график трафика, а графика в панели нет. Возвращаться к каналу
имеет смысл тогда, когда появится потребитель.

Проброс `Upgrade`/`Connection` и `proxy_http_version 1.1` в конфиге nginx оставлены на
месте и закреплены тестом: они ничего не стоят при отсутствующем канале и понадобятся,
если он появится.
