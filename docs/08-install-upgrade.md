# Установка, обновление, удаление

## Установка

```sh
curl -fsSL https://github.com/ArghTeam/razdacha/releases/latest/download/install.sh | sh
```

Скрипт лежит в `packaging/install.sh` и выкладывается ассетом каждого релиза.
`--dry-run` (или `RAZDACHA_DRY_RUN=1`) прогоняет только фазу проверок и выходит,
ничего не изменив, — этим же режимом проверяется машина перед установкой.

**Скрипт из релиза ставит свою версию.** При сборке релиза в копию скрипта
подставляется тег, под которым она выложена (`BUILT_TAG` в шапке), и дальше
ассеты качаются с `releases/download/<тег>/`. Иначе `install.sh` из `v0.1.1`
ставил бы последний релиз, и по имени ассета этого было бы не угадать.
В репозитории `BUILT_TAG` пустой: запуск из рабочей копии или из `main` ставит
последний релиз, как раньше. `RAZDACHA_VERSION=v1.2.3` перебивает и то, и другое.

Порядок шагов — важен именно такой, «сначала все проверки, потом все изменения»:

**Фаза 1 — проверки, система не трогается**
1. root, systemd, ядро ≥ 5.15, архитектура из поддерживаемых
2. дистрибутив из [матрицы](07-platform-support.md#матрица)
3. `systemd-detect-virt` — отказ на OpenVZ
4. `modprobe wireguard nft_tproxy nft_socket`, наличие `/dev/net/tun`
5. свободное место ≥ 100 МБ
6. конфликты: `wg0`, `wg-quick@wg0`, чужой `/etc/sing-box/config.json`,
   чужой `/etc/nginx/sites-available/razdacha` (файл без нашего заголовка-маркера)
7. определение внешнего адреса и WAN-интерфейса

**Фаза 2 — изменения**
8. установка `nginx`, если его нет: `apt-get install -y nginx`
9. загрузка `razdacha-linux-<arch>.tar.gz` из GitHub Releases, сверка
   `checksums.txt`, распаковка `razdachad` и `razdacha` в `/usr/local/bin`

Дальше всё делает сам бинарник — `razdacha setup`. Шагов на shell больше нет
сознательно: код установки уже написан и покрыт тестами
(`internal/packaging`), а вторая его реализация на shell отличалась бы от первой
собственным набором ошибок.

10. установка `sing-box` (пакет из репозитория подходящей версии, иначе бинарник
    в `/usr/local/bin`)
11. `net.ipv4.ip_forward=1` и `net.ipv4.ip_nonlocal_bind=1` →
    `/etc/sysctl.d/99-razdacha.conf`
12. генерация ключей сервера, инициализация БД, определение адреса подключения
13. сертификат панели в `/etc/razdacha/tls/` (см. ниже) и конфиг nginx
    в `/etc/nginx/sites-available/razdacha` + symlink в `sites-enabled`
14. первичный конфиг sing-box и юниты systemd
15. пароль панели и первый пир с именем `client-1`
16. `systemctl enable` + `systemctl restart` для `sing-box`, `razdachad` и nginx;
    `wg0` и nft-правила поднимает демон при старте

**Бинарник, а не `.deb`.** Пакета пока нет: он требует `nfpm` в сборке и
репозитория для обновлений, а до первого релиза важнее, чтобы установка вообще
существовала. Отсюда `/usr/local/bin`, а не `/usr/bin`: этот каталог не
принадлежит пакетному менеджеру, и апгрейд системы наш файл не тронет.
`ExecStart` в юните подставляется по факту, а не зашит.

**Фаза 3 — вывод**
```
  Готово.

  Отсканируйте QR-код клиентом WireGuard:

    ███████████████████████
    ██ ▄▄▄▄▄ █▀▄█ ▄▄▄▄▄ ███
    …

  Или скачайте конфиг:  /var/lib/razdacha/client-1.conf

  После подключения интерфейс будет доступен по адресу:
    https://10.8.0.1

  Режим панели:  приватный, панель доступна только из VPN.

  Сертификат самоподписанный — браузер предупредит при первом заходе.

  Не забудьте открыть UDP-порт 51820 в файрволе провайдера.
```

Последняя строка обязательна: у большинства облачных провайдеров есть внешняя группа
безопасности, о которой мы ничего не знаем. Это самая частая причина «установил, но не
подключается».

## nginx и сертификат

Панель стоит за nginx ([ADR 0008](decisions/0008-nginx-before-panel.md)). Установщик
делает с ним ровно три вещи:

1. **Сертификат.** Если `/etc/razdacha/tls/cert.pem` уже есть, разбирается, не просрочен
   и содержит **все** нужные IP в SAN — он остаётся как есть. Иначе генерируется новый:
   ECDSA P-256 средствами Go (не вызовом `openssl` — внешние бинарники мы не дёргаем),
   срок 10 лет. Каталог `0700`, ключ `0600`, сертификат `0644`.
   Перевыпускать самоподписанный сертификат по расписанию нечем и незачем, отсюда срок.

   SAN — `10.8.0.1`, а в публичном режиме ещё и внешний адрес сервера: при заходе по
   публичному IP без него браузер ругается на несовпадение имени, а это предупреждение
   страшнее и непонятнее, чем «неизвестный издатель». «Все нужные IP» здесь и есть
   условие перевыпуска при переходе в публичный режим: у выпущенного сертификата SAN
   сам не вырастет. Внешний адрес берётся из маршрутизации — UDP-сокет до публичного
   адреса без единого отправленного пакета показывает, каким адресом машина выходит
   наружу; ни root, ни интернет, ни сторонняя служба вроде `ifconfig.me` не нужны. Если
   адрес определить не удалось, установка не падает: сертификат выпускается на один
   `10.8.0.1`, а причина уходит в лог.
2. **Конфиг.** `/etc/nginx/sites-available/razdacha` генерируется кодом из настроек:
   адрес `wg0`, порты, пути к сертификату и ключу, адрес демона — подставляются, а не
   зашиты в файл-шаблон. Первая строка — заголовок-маркер `# razdacha: …`. Файл на этом
   пути без маркера считается чужим: установка останавливается с ошибкой и ничего не
   перезаписывает.
3. **Symlink.** `/etc/nginx/sites-enabled/razdacha` → на файл выше. Если по этому пути
   уже лежит symlink на наш файл — ничего не делается. Если что-то другое — ошибка.
4. **Снимает дефолтный сайт Debian** — `/etc/nginx/sites-enabled/default`. Пакет nginx
   включает его сам, а слушает он `listen 80 default_server` и `listen [::]:80
   default_server`, то есть `0.0.0.0:80` и `[::]:80` на публичном интерфейсе. Пока он
   включён, панель видна из интернета мимо нашего конфига: наш файл при этом безупречен,
   дыру создаёт чужой. Symlink снимается только если ведёт на `sites-available/default`;
   сам файл в `sites-available` не трогается, он принадлежит пакету. Факт снятия
   записывается в `/etc/razdacha/nginx-default-disabled.json`, и по этой отметке сайт
   возвращается при удалении. Symlink с именем `default`, ведущий куда-то ещё, — чужая
   настройка: не трогается, о чём пишется в лог.

Ничего другого в `/etc/nginx` не трогается: ни `nginx.conf`, ни файлы в
`sites-available`, ни чужие сайты.

## Почему nginx не стартует без `ip_nonlocal_bind`

nginx привязан к `10.8.0.1`, а этот адрес появляется вместе с `wg0`, который создаёт
демон. После перезагрузки nginx стартует раньше и падает с «cannot assign requested
address» — юнит уходит в `failed`, панель недоступна до ручного рестарта.

Лечится `net.ipv4.ip_nonlocal_bind=1` в том же `/etc/sysctl.d/99-razdacha.conf`:
процессу разрешается слушать адрес, которого ещё нет. Установщик пишет параметр в drop-in
(чтобы он пережил перезагрузку) и сразу проставляет его в `/proc/sys` (чтобы не ждать её).

Порядок юнитов через `After=` эту задачу не решает: `razdachad` может уже стартовать, а
`wg0` — ещё не подняться, и nginx снова не найдёт адрес.

**Если nginx не установлен**, установщик ставит его через `apt-get install -y nginx`.
Код настройки при отсутствии `/etc/nginx/sites-available` не падает с невнятной ошибкой
файловой системы, а сообщает: `nginx не установлен: каталог … не найден; установите
пакет: apt install nginx`.

## Режимы доступа к панели

По умолчанию nginx слушает только `10.8.0.1` — попасть на панель можно исключительно из
VPN ([модель привилегий](01-architecture.md#модель-привилегий)). Отсюда порядок:
установщик создаёт первого пира и печатает конфиг сам, иначе система была бы недоступна
для настройки.

В публичном режиме ([ADR 0009](decisions/0009-public-panel-access.md)) nginx слушает
`443` и `80` на всех интерфейсах; отдельного `listen` на `10.8.0.1` не нужно — он уже
покрыт, и изнутри VPN панель открывается как раньше. Вход прикрыт `limit_req` на
`POST /api/login`: зона `razdacha_login` на `$binary_remote_addr`, `10r/m` при всплеске
в 5 запросов, при превышении — `429`. Это заведомо выше живого человека с опечатками и
заведомо ниже перебора; точная защита — блокировка по адресу в самом демоне. Ограничение
висит только на входе: на `/` оно ломало бы панель, один экран тянет десятки запросов.

Режим — явный флаг, а не следствие настройки адреса: без него адрес вне приватного
диапазона и `0.0.0.0` по-прежнему отвергаются до генерации конфига. Демон в обоих
режимах сидит на `127.0.0.1:8080` и не виден даже из VPN.

**Режим переживает обновление.** Он хранится в БД (ключ `panel_public` в таблице
`settings`), потому что это свойство установки, а не аргумент запуска: обновление
документированным однострочником не передаёт никаких флагов, и без сохранённого
значения панель молча уходила из интернета. Порядок такой:

| что запустили | что получится |
| --- | --- |
| первая установка без флага | приватный режим, ключ не пишется |
| первая установка с `RAZDACHA_PUBLIC=1` | публичный, запоминается |
| первая установка с `RAZDACHA_PUBLIC=0` | приватный, **запоминается** |
| обновление без переменных, ключ в БД есть | режим, который был |
| обновление без переменных, ключа нет | режим выводится из конфига nginx и запоминается |
| обновление с `RAZDACHA_PUBLIC=1` | публичный, запоминается |
| обновление с `RAZDACHA_PUBLIC=0` | приватный, запоминается |

Флаг бинарника — `razdacha setup --public` и `razdacha setup --public=false`;
`install.sh` переводит в них `RAZDACHA_PUBLIC`. **Выключается тот же режим тем же
способом, которым включался** — `RAZDACHA_PUBLIC=0` (или `no`, `false`, пустая
строка). Отдельной команды `razdacha panel private` нет намеренно: второй вход в ту
же работу расходился бы с первым, ровно как в случае с `razdacha update`.

**Явно заданный флаг записывается всегда**, даже когда он совпадает со значением по
умолчанию. «Сознательно выбрал приватный режим» и «никогда не спрашивали» — разные
состояния, и различать их надо до первого обновления, а не после: второе состояние
разбирается догадкой по конфигу nginx (ниже), первое — нет.

**Ключа может не быть.** Версии до 0.2.1 его не писали, и на обновлении с них читать
нечего: панель уходила из интернета молча (issue #81). Поэтому при отсутствующем ключе
режим выводится из уже лежащего конфига nginx — того самого, который мы же и
генерировали:

| что лежит в `sites-available/razdacha` | вывод |
| --- | --- |
| наш конфиг, `listen 443 ssl` (без адреса) | публичный, записывается в БД |
| наш конфиг, `listen 10.8.0.1:443 ssl` | приватный, записывается в БД |
| конфига нет вовсе | первая установка: приватный, ничего не пишется |
| конфиг не читается, без маркера или без разбираемого `listen` | приватный, **ничего не пишется**, причина печатается в выводе |

Разбирается та же директива, которую генерирует `SiteConfig.Render`, и по тому же
правилу, что и в `Validate`: отсутствие адреса и адрес вне приватного диапазона —
публичный режим. Догадка делается один раз: выведенный режим сразу записывается,
и следующее обновление читает уже ключ.

Неразобранный конфиг — единственный случай, когда режим остаётся неизвестным. Установка
на этом не останавливается (панель без nginx-конфига бесполезнее, чем панель в приватном
режиме), но и записать догадку нечем: в БД не пишется ничего, а в выводе печатается
причина и команда `RAZDACHA_PUBLIC=1`. Иначе повторилась бы ровно та же беда — тихий
уход из интернета.

Смена режима видна в выводе: установщик печатает, в каком режиме панель осталась, и
отдельно отмечает, что этот запуск режим изменил или что режим взят из существующего
конфига. Ключ лежит рядом с настройками, но в `store.Settings` не входит и в
`GET /api/settings` не попадает — как и хеш пароля: `PATCH /api/settings` из панели не
должен уводить панель из интернета.

Настройки хранят и версию установки (`installed_version`) — по ней называется
резервная копия при обновлении.

## Идемпотентность

Повторный запуск `install.sh` на настроенной системе выполняет обновление, а не
переустановку: ключи сервера, пиры, туннели и правила сохраняются. Проверка — наличие
`/var/lib/razdacha/state.db`.

То же и для nginx: конфиг переписывается, только если его содержимое отличается от
сгенерированного; symlink не дублируется; валидный сертификат не перевыпускается.

## Обновление

```sh
curl -fsSL https://github.com/ArghTeam/razdacha/releases/latest/download/install.sh | sh
```

Отдельной команды `razdacha update` нет: тот же скрипт и есть обновление, а вторая
точка входа в ту же работу только расходилась бы с первой.

1. фаза проверок, как при установке; наличие `state.db` переводит её в режим обновления
2. скачивание архива для текущей архитектуры и сверка `checksums.txt`
3. замена бинарников в `/usr/local/bin`
4. **резервная копия БД** в `/var/lib/razdacha/backups/state-<version>-<время>.db` —
   снимается до открытия БД, потому что миграции накатываются при открытии и назад не
   откатываются: вернуться на прошлую версию можно только возвратом файла.
   `<version>` — **версия, состояние которой в копии лежит**, то есть та, что стояла
   до обновления: копия и есть путь отката, и назвать её версией, на которую
   обновляемся, значит соврать в имени файла. Версия читается из самой БД (ключ
   `installed_version`) отдельным чтением, без миграций — они бы уже изменили файл.
   Копии, снятые при обновлении с версий до 0.2.1, называются `state-unknown-<время>.db`:
   те версии свою версию в БД не записывали, и придумать её задним числом нечем
5. миграции схемы, регенерация конфига nginx и первичного конфига sing-box
6. `systemctl enable` + `systemctl restart` для `sing-box`, `razdachad` и nginx.
   Именно `restart`, а не `enable --now`: на уже работающем юните `--now` не делает
   ничего, и после обновления в памяти оставался старый процесс — новый бинарник на
   диске, `/proc/<pid>/exe` с пометкой `(deleted)`, и ни одно изменение демона до
   пользователя не доезжало. Рантайм перезапускается по той же причине и ещё одной:
   конфиг генерируется целиком, и кэш FakeIP обязан обнулиться вместе с ним
7. `Type=notify` держит `systemctl start` до тех пор, пока `wg0` не поднят и правила не
   залиты, — «готово» не печатается раньше времени

Конфиг nginx на обновлении пересобирается тем же кодом и переписывается, только если
изменился; сертификат, если он валиден, не перевыпускается — иначе у пользователя каждый
раз слетало бы исключение, добавленное в браузере.

Путь к резервной копии печатается в лог установки: если миграция сломала состояние,
возврат — это `systemctl stop razdachad`, копирование файла обратно и старт.

**Клиентские конфиги при обновлении не меняются** — ключи, адреса и порт сохраняются.
Исключение — смена `client_mtu` или `wg_pool` в новой версии; такие изменения требуют
явного действия пользователя и не применяются автоматически.

## Systemd-юнит

```ini
[Unit]
Description=razdacha selective VPN gateway
After=network-online.target
Wants=network-online.target

[Service]
Type=notify
ExecStart=/usr/local/bin/razdachad
Restart=on-failure
RestartSec=5

NoNewPrivileges=yes
ProtectSystem=strict
ProtectHome=yes
ReadWritePaths=/var/lib/razdacha /etc/razdacha /etc/sing-box
PrivateTmp=yes
RestrictAddressFamilies=AF_INET AF_INET6 AF_NETLINK AF_UNIX
CapabilityBoundingSet=CAP_NET_ADMIN CAP_NET_RAW CAP_NET_BIND_SERVICE

[Install]
WantedBy=multi-user.target
```

`Type=notify` — демон сообщает о готовности после того, как `wg0` поднят и nft-правила
залиты, а не сразу при старте процесса. Сообщение — датаграмма `READY=1` в
`$NOTIFY_SOCKET` (`cmd/razdachad/notify.go`); библиотеки для этого не нужны, а
`go-systemd` тянул бы за собой d-bus.

`ReadWritePaths` обязан включать `/etc/sing-box`: при `ProtectSystem=strict` без него
запись сгенерированного конфига падает по правам, и в панели это выглядит как
«внутренняя ошибка» на кнопке «Применить».

**Юнит sing-box.** Если рантайм пришёл пакетом дистрибутива, используется его штатный
юнит и ничего не подменяется: обновляет его пакетный менеджер, а наш файл в
`/etc/systemd/system` перекрыл бы его навсегда. Если бинарник положили мы, юнит пишем
тоже мы — с маркером в первой строке и **без `ExecReload`**. Это не упущение:
`systemctl reload-or-restart` при отсутствии `ExecReload` перезапускает сервис, а нам
нужен именно перезапуск — конфиг генерируется целиком, и кэш FakeIP обязан обнулиться
вместе с ним, иначе клиент с закэшированным адресом уходит в никуда.

## Удаление

```sh
razdacha uninstall
```

Восстанавливает исходное состояние системы:

1. остановка и отключение юнитов
2. удаление `wg0`
3. удаление таблицы `inet razdacha`, `ip rule` и таблицы маршрутизации 105
4. удаление `/etc/sysctl.d/99-razdacha.conf` и сброс `net.ipv4.ip_nonlocal_bind` в
   работающем ядре
5. снятие symlink `/etc/nginx/sites-enabled/razdacha` и файла
   `/etc/nginx/sites-available/razdacha`, возврат дефолтного сайта Debian, если снимали
   его мы, затем `systemctl reload nginx`
6. снятие наших юнитов systemd и `/etc/sing-box/config.json`, `systemctl daemon-reload`
7. спрашивает отдельно: удалять ли `/var/lib/razdacha` (пиры и ключи) и `sing-box`

Флаги для неинтерактивного запуска: `-purge` (удалить состояние), `-keep-data`
(оставить), `-remove-singbox`, `-yes`. Без терминала на том конце вопрос не задаётся
вовсе и ответом считается «нет»: скрипт не должен ни зависать на приглашении, ни
удалять ключи оттого, что stdin оказался пустым.

Ни один шаг не прерывает остальные: всё, что не снялось, собирается в итоговую ошибку
списком. Половина снятого хуже, чем внятный отказ в конце.

**`net.ipv4.ip_forward` остаётся включённым, и об этом говорится вслух.** Из двух
параметров ядра сбрасывается только `ip_nonlocal_bind`: он экзотический и нужен
исключительно нам. Маршрутизацию же включают все подряд — docker, другой VPN,
пробросы администратора, — и выключить её значит оборвать чужую работу на той же
машине; узнать, кто включил её первым, нечем: в `/proc/sys` истории нет. Раньше эта
асимметрия была молчаливой, а команда печатала «система возвращена в исходное
состояние». Теперь, если параметр остался в единице, удаление печатает это отдельной
строкой вместе с командой, которой его выключают вручную (`sysctl -w
net.ipv4.ip_forward=0`).

Сами бинарники `/usr/local/bin/razdachad` и `/usr/local/bin/razdacha` остаются: команда
работает из одного из них, и удалять их из-под себя — лишний способ оборвать удаление на
середине. Их сносит одна строка, которую печатает сама команда.

Шаг 5 избирателен: symlink снимается, только если он ведёт на наш файл, а файл удаляется,
только если в нём есть заголовок-маркер. Чужой конфиг с тем же именем остаётся на месте.
Дефолтный сайт возвращается только при наличии отметки `/etc/razdacha/nginx-default-disabled.json`
— если пользователь выключил его сам, удаление razdacha не включит его обратно.
Сам nginx не удаляется — его могли поставить до нас и использовать для другого.
Сертификат лежит в `/etc/razdacha/tls/` и уходит вместе с `/etc/razdacha`.

Podkop показывает, почему это важно: там неполная очистка (остатки в
`/etc/iproute2/rt_tables`, изменённый `/etc/config/dhcp`) — постоянный источник проблем
при переустановке. Все системные изменения должны быть перечислены и обратимы; тест на
чистое удаление — часть CI.

## Ручное восстановление

Если демон не стартует, интернет у клиентов не должен пропадать полностью. Прямой путь
(masquerade) не зависит от sing-box, а nft-правила остаются в ядре после остановки
демона — теряется только селективность. Для полного сброса:

```sh
razdachad --reset-network     # снять nft-правила, ip rule, маршруты; wg0 оставить
```
