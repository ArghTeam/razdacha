## TLDR

Job `singbox-check` в CI: скачивает релизный бинарник `sing-box` версии, взятой из
`go.mod`, и прогоняет `sing-box check -c` по всем фикстурам
`internal/singbox/testdata/*.json`. Бинарник кэшируется по ключу с версией.

## Goal

Golden-тесты сравнивают вывод генератора с нашими же ожиданиями и не ловят «sing-box
такой конфиг не принимает». Конституция требует `sing-box check` перед применением —
на проде проверка есть, в разработке её не было, и расхождение вскрылось бы уже на
живом сервере.

## Domains touched

- [packaging](../context/packaging/index.md) — состав проверок CI, версии инструментов
- [singbox](../context/singbox/index.md) — golden-фикстуры генератора конфига

## Decisions

- 2026-07-25 — версия читается из `go.mod` через `go mod edit -json` + `jq`, а не
  задаётся числом в workflow: дублирование числа и есть тот дрейф версий, ради
  которого задача заведена.
- 2026-07-25 — тег релиза и имя ассета различаются формой (`v1.12.25` против
  `1.12.25`), поэтому шаг отдаёт два output'а — `tag` и `version` — вместо угадывания
  на месте.
- 2026-07-25 — после распаковки job сверяет `sing-box version` с версией из `go.mod`:
  если ассет когда-нибудь окажется не тем, job упадёт на сверке, а не проверит конфиг
  чужим бинарником.
- 2026-07-25 — `setup-go` берётся с `cache: false`: Go нужен только для чтения
  `go.mod`, кэш модулей здесь ничего не ускоряет.
- 2026-07-25 — цикл по фикстурам не прерывается на первой ошибке (`|| status=1`):
  в логе видно состояние всех конфигов, а не только первого сломанного.

## Acceptance criteria

- [x] `sing-box check` проходит по `empty.json` и `full.json`
- [x] заведомо невалидный конфиг роняет job (проверено локально: неизвестный тип
      outbound — `FATAL ... unknown outbound type`, код возврата 1)
- [x] версия sing-box в job берётся из `go.mod`, дублирования числа нет
- [x] бинарник кэшируется по ключу `sing-box-<тег>-linux-amd64`, job не удлиняет CI
      больше чем на минуту
