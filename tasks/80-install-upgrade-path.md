## TLDR
Путь обновления сломан в released `v0.2.0`: демон не перезапускается, а публичный режим
молча теряется. Плюс три мелочи в установщике и удалении. Всё это один слой и два файла,
поэтому чинится одной задачей. Закрывает #80, #81, #82.

## Goal
Обновление документированным однострочником даёт работающую новую версию и не меняет того,
о чём не просили.

## Domains touched
- [packaging](../context/packaging/) — установка, обновление, удаление, параметры ядра
- [store](../context/store/) — режим доступа к панели как сохранённая настройка

## Decisions
- 2026-07-26 — **Режим панели хранится в настройках** (`store`, key/value с дефолтами в
  коде), а не только во флаге. Приоритет: `--public` задаёт и запоминает; без флага берётся
  сохранённое; первая установка без флага — приватный режим, как сейчас. Причина: режим —
  свойство установки, а не аргумент запуска, и его потеря при обновлении уводит панель из
  интернета молча (#81).
- 2026-07-26 — Демон при обновлении перезапускается явно, как это уже сделано для nginx
  (`setup.go:462`). `systemctl enable --now` на активном юните не перезапускает, и новая
  версия не доезжает до пользователя вовсе (#80).
- 2026-07-26 — Задачи не разводятся по веткам: все три сходятся в `cmd/razdacha/setup.go` и
  `packaging/install.sh`, параллельная работа дала бы конфликты и риск противоречащих правок
  в одной функции.
- 2026-07-26 — `install.sh`, выложенный под тегом, по умолчанию ставит свою версию.
  Сейчас он хардкодит `releases/latest/download/`, и ассет из `v0.1.1` ставит `v0.2.0`.
  `RAZDACHA_VERSION` продолжает переопределять (#82).
- 2026-07-26 — Тег подставляется в скрипт **при сборке релиза** (`BUILT_TAG` в шапке,
  `sed` в workflow), а не вычисляется скриптом на машине: узнать свой тег через
  `curl … | sh` скрипту неоткуда, а ходить в API GitHub он не должен — на этом держится
  весь путь `/releases/latest/download`. В репозитории `BUILT_TAG` пустой, и запуск из
  `main` по-прежнему ставит последний релиз.
- 2026-07-26 — Режим панели и версия установки хранятся ключами `panel_public` и
  `installed_version` в таблице `settings`, но **вне `store.Settings`** — как хеш пароля
  (`auth.go`). Иначе `PATCH /api/settings` из панели переписывал бы режим вслепую, а
  слои `api` и `ui` пришлось бы трогать этой задачей.
- 2026-07-26 — Выключается публичный режим тем же флагом, которым включался:
  `razdacha setup --public=false`, через установщик `RAZDACHA_PUBLIC=0`. Отдельной
  команды (`razdacha panel private`) нет по той же причине, по какой нет
  `razdacha update`: вторая точка входа в ту же работу расходится с первой.
- 2026-07-26 — Версия для имени резервной копии читается из файла БД **отдельным
  чтением без миграций** (`store.InstalledVersionAt`): копия снимается до `store.Open`,
  а после него файл уже мигрирован. Копии с версий до 0.2.1 называются
  `state-unknown-<время>.db` — те сборки версию в БД не писали.
- 2026-07-26 — `ip_forward` при удалении **не сбрасывается**, но об этом печатается
  строка с командой ручного выключения. Причина: `ip_nonlocal_bind` экзотический и
  нужен только нам, а маршрутизацию включают docker, другой VPN и руки администратора;
  кто включил её первым, узнать нечем — истории в `/proc/sys` нет. Обрывать чужую
  работу хуже, чем оставить параметр включённым и сказать об этом.

- 2026-07-26 — **Доделка после проверки на стенде.** Механики хранения режима мало:
  `v0.2.0` ключ `panel_public` не писала, поэтому при обновлении с неё `ensurePanelMode`
  читает пустоту, получает `false` и уводит панель в приватный режим — молча, потому что
  `opts.public == saved` считается «ничего не изменилось». При отсутствующем ключе режим
  выводится из уже лежащего конфига nginx и записывается в БД: публичный `listen` означает
  публичную установку. Разовая миграция, дальше ключ всегда есть.
- 2026-07-26 — Явно заданный флаг записывается в БД всегда, даже когда совпадает со
  значением по умолчанию: «сознательно выбрал приватный» и «никогда не спрашивали» — разные
  состояния, и различать их надо до первого обновления, а не после.

## Notes
- Курицы и яйца нет: `install.sh:367` запускает свежераспакованный `razdacha setup`,
  поэтому исправление перезапуска сработает уже на первом обновлении `v0.2.0 → v0.2.1`.
- Замер, которым дефект пойман на стенде: после обновления `MainPID` остался прежним,
  `ExecMainStartTimestamp` — раньше времени обновления, `/proc/<pid>/exe` помечен
  `(deleted)`. Установщик при этом печатал «сервисы запущены» и «Обновление завершено».
- Публичный режим терялся так: `opts.public` берётся только из флага, `install.sh`
  передаёт его лишь при `RAZDACHA_PUBLIC` в окружении, в БД режим не хранится — nginx
  перегенерировался приватным и панель пропадала из интернета.
- `ip_forward` при `-purge` не сбрасывается, хотя `ip_nonlocal_bind` сбрасывается.
  До нас его мог включить кто-то другой, поэтому «не трогать» — допустимый ответ, но тогда
  это должно быть сказано в выводе, а не молчаливо.
- Утечка сертификата при `-purge` уже вылечена (9f157ed) и подтверждена на стенде — не
  трогать, только не сломать.

## Acceptance criteria
- [x] После обновления работает новый бинарник: `ExecMainStartTimestamp` позже времени
      обновления, `/proc/<pid>/exe` без пометки `(deleted)`; на первой установке поведение
      прежнее — юниты получают `enable` + `restart`
- [x] Обновление без переменных окружения сохраняет режим панели; `RAZDACHA_PUBLIC=1`
      по-прежнему переключает, `RAZDACHA_PUBLIC=0` выключает; смена режима видна в выводе
- [x] `install.sh` из релиза по умолчанию ставит свою версию, `RAZDACHA_VERSION` работает
- [x] Имя резервной копии называет сохранённую версию, а не ту, на которую обновляемся
- [x] Поведение с `ip_forward` объяснено в выводе удаления
- [x] Проверено на стенде прогоном `v0.2.0 → v0.2.1`: #80 и #82 подтверждены, #81 провален
- [ ] Обновление публичной установки с `v0.2.0` сохраняет публичный режим: ключа в БД нет,
      режим выведен из конфига nginx и записан — проверено на стенде
- [ ] Явный `RAZDACHA_PUBLIC=0` при отсутствующем ключе записывает выбор в БД
