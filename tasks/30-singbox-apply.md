## TLDR

Применение конфига sing-box: `singbox.Applier` генерирует конфиг целиком из снимка
БД, сравнивает с лежащим на диске, пишет во временный файл рядом, прогоняет по нему
`sing-box check`, атомарно переименовывает в `/etc/sing-box/config.json` и делает
`systemctl reload sing-box`. Наружу это выходит как `POST /api/apply`. Рантайм
ставит `packaging.SingboxInstaller` — версией с версией библиотеки из `go.mod`.

## Goal

Генератор из #3 собирал конфиг в память и никуда его не отдавал: панель могла
править состояние, но маршрутизация от этого не менялась. Задача замыкает цепочку
«состояние БД → работающий sing-box» так, чтобы битый конфиг не мог затереть
рабочий, а причина отказа доходила до пользователя текстом.

## Decisions

- 2026-07-25 — сравнение с диском идёт **до** проверки и по самим байтам, а не по
  md5 (Podkop: `podkop/files/usr/bin/podkop:1256`). Файл читается в любом случае,
  а хеш только добавил бы шанс совпасть при разном содержимом. Совпало — сервис не
  трогаем вовсе: ни временного файла, ни `check`, ни `reload`.
- 2026-07-25 — `check` прогоняется по временному файлу в каталоге целевого:
  проверяется ровно тот файл, который станет конфигом, а `rename` в пределах
  каталога атомарен. Отказ проверки удаляет временный файл и оставляет рабочий
  конфиг нетронутым.
- 2026-07-25 — права конфига `0600`: в нём приватные ключи туннелей. Штатный юнит
  sing-box работает от root, читать нечего никому больше.
- 2026-07-25 — `check` и `reload` — интерфейсы `Checker`/`Reloader`, реализации
  `BinaryChecker` (`sing-box check -c`) и `SystemctlReloader` (`systemctl reload`).
  В тестах подменяются, поэтому весь слой применения тестируется без root и без
  установленного рантайма.
- 2026-07-25 — `systemctl` инварианту «netlink вместо бинарников» не противоречит:
  тот про `nft`/`ip`/`wg`, где у нас есть свой интерфейс к ядру. Здесь мы управляем
  чужим сервисом, и его публичный интерфейс — юнит.
- 2026-07-25 — провал `reload` не откатывает файл: конфиг валиден и уже на диске,
  следующий старт сервиса его подхватит. Ответ — `500`, а не `422`.
- 2026-07-25 — отказ `sing-box check` отдаётся как `422` с кодом `invalid_config` и
  текстом рантайма целиком (docs/05-api.md). Ошибка генерации — тот же `422`:
  для пользователя это одно и то же «конфигурацию применить нельзя».
- 2026-07-25 — `Config.Applier` пустым означает настоящий `singbox.NewApplier()`,
  поэтому демон не надо перепроводить в `main.go`, а тесты подставляют свой.
- 2026-07-25 — установка рантайма: уже стоящий в системе `sing-box` подходит, если
  его версия равна версии библиотеки (это и есть ветка «пакет из репозитория»);
  иначе кладётся бинарник релиза той же версии в `/usr/local/bin`, а не в
  `/usr/bin` — тот принадлежит пакетному менеджеру. Версия библиотеки читается из
  вшитой информации о сборке (`debug.ReadBuildInfo`), то есть из того же `go.mod`,
  что и в CI; версия рантайма — последним полем первой строки `sing-box version`,
  тем же разбором, что `awk 'NR==1 {print $NF}'` в job `singbox-check`.

## Acceptance criteria

- [x] битый конфиг не применяется и не затирает рабочий
- [x] неизменившийся конфиг не вызывает перезагрузку сервиса
- [x] ошибка `sing-box check` доходит до пользователя текстом, а не кодом
- [x] версия рантайма сверяется с версией библиотеки из `go.mod`
- [x] тесты идут без root и без установленного sing-box: запись во временный
      каталог, `check` и `reload` подменяются
- [x] `POST /api/apply` без сессии — 401, с сессией — результат применения
